## 1. ЦЕЛЬ И КУДА ДОВОДИТЬ (definition of done)

### Конечное состояние
**Рабочий тайлинговый оконный менеджер на macOS, который выглядит и ощущается 1:1 как
линуксовый Hyprland пользователя.** Не демка, не «похоже» — среда на каждый день.
Приёмка = визуально и по ощущению неотличимо от его Hyprland: тайлинг-раскладка, те же
анимации, то же стекло-блюр, скругления, тени, те же бинды.

### Принципы (его слова)
- **1:1 с Hyprland, без компромиссов.** Планка — его линуксовый конфиг (§7), который сам
  был зеркалом его же макового OmniWM. Эталон поведения он знает наизусть.
- **Работать ВНУТРИ WindowServer**, двигать окна его же серверными функциями. БЕЗ
  Accessibility API (это OmniWM — дёрганый, уже есть, не нужен). Без межпроцессной
  возни. В ядро не лезть.
- **НЕ порт Wayland.** Нужно ПОВЕДЕНИЕ, а не портирование кода. Можно смотреть исходники
  Wayland/Hyprland и переписывать логику под мак — но результат судится по поведению.
- **Resize — настоящий, нативный.** Разобрать, как сервер просит приложение
  перерисоваться в новый размер (аналог configure в Wayland), и пользоваться этим. Пока
  нативный путь не найден — не скатываться на масштаб слоя. Масштаб (мылит текст) —
  запасной план и только для окон, где нативно вообще никак.
- **Блюр/прозрачность — выжать максимум, не бросать на полпути.** Мы внутри WS и видим
  все IOSurface. Делать настоящий блюр под окнами: брать пиксели нижних слоёв и мылить
  Metal-шейдером (dual-kawase, как Hyprland) для окон, отдающих прозрачный буфер
  (терминалы и т.п.). Для окон, рисующих себя сплошняком — решить, что выглядит лучше в
  этих рамках. Параметры — из §7.
- **Техника — на агенте.** Пользователь делегирует технические решения. Сам выбирай
  подход, сам определяй границу и **честно говори, где упёрлись в САМО приложение (не
  отдаёт прозрачный буфер / не слушает resize), а не в наш код.**

### Порядок работ
1. ✓ Рисуем свои пиксели в кадре (красный прямоугольник).
2. ✓ Двигаем реальное окно по позиции (серверной функцией изнутри WS).
3. ✓ (механизм) Плавность: переезд со spring drift через трансформ окна + свой тик на
   таймере главного потока WS (§5 «Плавный переезд»). Ждёт приёмки глазами.
4. → Движок раскладки (dwindle) + бинды → реальный тайлинг реальных окон.
5. Визуал до 1:1: анимации (§7), блюр dual-kawase (сэмплинг IOSurface снизу),
   скругления, тени, бордеры-градиент, glow.
6. Параллельно: нативный resize (приоритет, §6).

## 4. КАК РАБОТАТЬ С ЖИВЫМ WindowServer (критичные правила)

- **lldb при подключении замораживает экран** на время attach (неск. сек) — норма,
  отпускает при detach. НО: никогда не ставить брейк в ГОРЯЧЕМ пути (`composite()` и всё,
  что зовётся каждый кадр) и не держать процесс стоящим — зависание = чёрный экран.
  Брейки только на РЕДКИХ функциях (срабатывают на действие пользователя).
- **Баг-заморозка:** python `SetAsync(True); Continue(); time.sleep()` в `lldb --batch`
  не прокачивает event-loop → процесс стоит на брейке и ЭКРАН ЗАМЕРЗАЕТ. Не использовать.
- **Live-чтение аргументов без заморозки** (работает): брейк с флагом `-G true`
  (auto-continue) + `-C 'register read ...'` + `-C 'memory read ...'`, затем
  `-o continue`, lldb в ФОНЕ; через N сек завершить lldb через dtrace (процесс сам
  продолжает работу). Всегда после — проверить `pgrep -f 'lldb -p <pid>'` и `ps -o stat`
  (иногда сторож не доводит — завершить вручную).
- **Вызов серверной функции из lldb на arm64e — только по ИМЕНИ СИМВОЛА**, не по
  числовому адресу. Числовой каст → lldb подписывает указатель не так, как надо →
  EXC_BAD_ACCESS `0xd63f091f`. Правильно: `((RET(*)(ARGS))SymbolName)(args)` — каст
  символа к типу (debug-инфо нет, тип задаём сами).
- **screencapture не видит наш рисунок** (идёт через другой путь композита) — результат
  проверять ГЛАЗАМИ пользователя, не скриншотом.

## 5. РАБОЧИЕ РЕЦЕПТЫ (проверены)

### Наш колбэк в кадре (список metalCallbacks) — `/tmp/memhook_red.py`
1. slide: `t.FindSymbols("metalCallbacks")[0].GetStartAddress().GetLoadAddress(t)` −
   статик `0x1ea5fb3b8`. (slide меняется каждый boot.)
2. Два mmap: `(void*)mmap(0,16384,3,0x1002,-1,0)` — код и данные РАЗДЕЛЬНО.
3. код колбэка → код-регион; `mprotect(code,16384,5)` R+X (данные оставить RW! иначе
   SIGBUS при записи — W^X: исполняемая и записываемая страницы разные).
4. подпись указателя (arm64e, ключ IA, модификатор 0 — как ждёт диспетчер `blraaz`):
   `(void*)__builtin_ptrauth_sign_unauthenticated((void*)A,0,0)` (ключ IA задаём ЧИСЛОМ
   0; макрос `ptrauth_key_asia` в выражении lldb без #include = 0, не использовать).
5. узел `{next=*head, signed_fn, ctx}` в данные; `*head = node` (процесс стоит, гонок нет).
6. Снять колбэк без перелогина: записать 0 в head списка `metalCallbacks`.
- Колбэк зовётся как `(x0=MetalContext*, x1=&shared_ptr<Display>, x2=0, x3=node.ctx)`.

### Рисовать прямоугольник: `metal_clear_rect(MetalContext*, float scale, CGRect, float4 color)`

### Двинуть окно (позиция, нативно): `CGXMoveWindowList` — `/tmp/movewin.py`

### Трансформ окна (основа анимаций): `CGXSetWindowTransform3DList` — `hook/scripts/xform.py`
`(conn, uint* wid, uint* key, CATransform3D* m)`, static `186e4fcf4`, обрабатывает 1 окно.
- **key** = слот в стеке трансформов окна. Клиентский путь `SLSTransactionSetWindowTransform3D`
  шлёт `0x30000000` — его и используем. Стек: записи 0x90 `{key, flags, conn_id, 0, m[16]}`,
  сортировка по key; функция заодно сбрасывает системные слоты 0x1ffffffe/0x1ffffffd.
- **Identity-матрица удаляет слот** (`window_set_transform` → CATransform3DIsIdentity).
- **Матрица мапит ЭКРАН→ОКНО**: translate (120,80) сдвинул окно на (−120,−80). Визуальный

### Таймер главного потока WS (покадровый драйвер)
`reschedule_callback_on_session(&gMainThreadQueue, fn, ctx, session, policy=0, nodelay=1, double fire_at)`

fn подписан IA/0 (paciza), таймер ОДНОРАЗОВЫЙ (перепланировать себя). **session обязателен**:
при NULL колбэк не зовётся (лог ошибки). session = `*(*(__sessionControlRef)+0x20)` — так

серверные функции. (Апловский движок `PKGAnimation*`/`PKGWindowTransformAnimationCreate`
тоже есть, но кривые там их — не трогали.)
