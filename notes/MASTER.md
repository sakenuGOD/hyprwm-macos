## 1. Принципы работы

- Это личный проект кастомизации рабочего стола на собственной машине пользователя. Разбор недокументированных
  системных фреймворков (SkyLight, QuartzCore, AppKit) статикой и живой отладкой — штатный и ожидаемый метод
  этого проекта, а не исключение.
- Если правильное решение требует разобрать внутренности системы глубже — агент делает этот разбор, а не выбирает
  обходной путь только потому, что он проще. Критерий выбора — что даст результат ближе к 1:1 Hyprland по
  плавности и виду, а не что легче реализовать.
- Каждая находка проверяется по бинарнику (адрес в `/tmp/sl_map.tsv`, листинг `/tmp/sl_dis.txt`, `nm`/`otool`)
  или вживую **до того**, как на ней строится следующий шаг. В отчётах «проверено» [V] и «гипотеза» [H]
  всегда разделены.
- Честно помечать, где предел задаёт само приложение или система (например, скорость перерисовки Telegram),
  а где — наш код.
- Временные обходы допустимы только как явно помеченная ступенька к настоящему решению, с записью, какое
  решение их заменит (в этом документе такие места помечены «ступенька → заменит …»).
- Пользователь дал согласие на загрузку нашего кода в процессы его приложений (Telegram, Finder, Ghostty и т.д.)
  для «всегда активного вида» окон (§9.4, шаг П3 плана).

## 2. Правила безопасности (обязательны)

1. **К живому WindowServer обращается только один агент за раз.** Исследователи — только статика.
2. **Движок переустанавливать только перезапуском демона** (`hook/stop.sh` → `hook/start.sh`). Демон сам
   переставляет движок при смене сборки (mtime `anim4.bin` > `anim4.state`), создаёт **новый** файл канала на
   каждую установку и проверяет `h.size`.
3. **Никогда не пересоздавать файл канала под живым движком** — так упала сессия в 20:27 (WS читает канал через
   `mmap MAP_SHARED`).
4. lldb: брейки только на редких функциях; **никогда** в горячем пути (`composite()`, `UpdateDisplays`, всё, что
   зовётся каждый кадр). Не использовать `SetAsync(True); Continue(); sleep()` в `lldb --batch` (замораживает экран).
   Чтение аргументов — только брейк с `-G true` (HANDOFF §4).
5. Вызов серверной функции из lldb на arm64e — только по имени символа, не по числовому адресу (HANDOFF §4).
6. Всё обратимо: сбой WS = перелогин сессии (`sudo killall WindowServer` с телефона по SSH), данные целы. Перед
   опытом с живым WS — Logic закрыт, пользователь предупреждён.
7. Жёсткие смещения внутри структур WS (`win+0x30` соединение, `win+0x170` форма, `win+0x18` CAWindowContent и
   т.д.) верны для **macOS 26.7.1 (25G241)**. После обновления системы — сверить заново (сейчас проверки сборки в
   `install4.py` нет — skeptic S11, баг P31).
8. Перед изменением кода — прогнать соответствующий стресс-сценарий из `notes/research/skeptic.md` §3 (T1–T9) до и
   после; запись экрана — `hook/scripts/rec2.py` (видит наш трансформ и клип; ScreenCaptureKit — не видит).

## 3. Цель и критерии приёмки «1:1 Hyprland»

Источник: `GOAL.md` §1, `HANDOFF.md` §1, `notes/hyprland_spec_full.md` §1–§8.

Цель: рабочий тайлинговый WM на macOS, неотличимый по виду и ощущению от линуксового Hyprland пользователя
(Hyprland 0.56.2, hyprutils 0.14.2; конфиг `~/arch-nebula/dotfiles/home/.config/hypr/`). Монитор пользователя —
2560×1440@180 Гц; мак — MacBook Air M4, 60 Гц.

Критерии приёмки (числа — spec §1.2–§1.5, §3–§5):

| # | Критерий | Число / кривая | Как проверять |
|---|---|---|---|
| A1 | Все окна события стартуют в одном кадре, одна волна, без поздних коррекций | один t0 на пачку | rec2: все окна сдвинулись в одном кадре; монотонная скорость без второго разгона |
| A2 | Задержка «нажатие → первый сдвиг» | ≤ 1 кадр + 5 мс (≤22 мс) | лог времени приёма команды vs `h.te` первого тика; телефон 120–240 к/с с keycastr |
| A3 | Перекладка/resize — пружина drift | m1 k210 d24; ряд @60 Гц `0.026 0.089 0.176 0.273 0.373 0.470 …`, перелёт 0.97% на 387 мс | журнал траектории движка (timing §5 шаг 2), ±0.5 pt |
| A4 | Содержимое при resize | буфер 1:1 от левого верхнего угла, обрезка (бокс < буфера) / дотяжка краевых пикселей (бокс > буфера); конечный размер приложению сразу и один раз | кадр в середине анимации: нет серых полос, нет растяжения текста |
| A5 | Открытие окна | windowsIn: popin 86% + bounce (k260 d20, пик 101.2%), fadeIn smooth 300 мс; без мелькания на «родном» месте | rec2: первый кадр окна уже α<0.2 и в плитке |
| A6 | Закрытие окна (любое, включая Cmd+W) | windowsOut: popin 92% snappy 260 мс + fadeOut 240 мс; соседи стартуют в том же кадре | rec2: ≥14 кадров призрака |
| A7 | Рабочие столы | slidefade 12% ширины (на Air ≈176 pt) + альфа, drift, обои/меню стоят | rec2: все окна обоих столов в одном кадре |
| A8 | Фокус за мышью | рамка 2 px, градиент primary→tertiary 45° (α 0.933), неактивная outline_variant α 0.333, кроссфейд 600 мс; тень 0.467↔0.267 и glow 0.2↔0 за 800 мс | rec2 при наведении |
| A9 | Оформление | скругление 18, суперэллипс p=2.6; тень range 34, offset (0,10), профиль (1−e/34)^3 (≈гаусс σ≈11 ×1.95); glow внутрь 18; блюр dual-kawase size 5 passes 2 (σ≈10.4 px), brightness 0.92, vibrancy 0.22 | наложение кадра на `evidence/linux_ref` |
| A10 | Неактивные окна | выглядят так же, как активные (в Hyprland «серого» вида нет) | видео: 0 серых кадров при follow_mouse |
| A11 | Нет промежуточных артефактов | 0 кадров с прямыми углами, серыми прямоугольниками, окнами вне плиток | rec2 на всех сценариях T1–T9 |
| A12 | Настраиваемость | все значения берутся из его Lua-конфига (`hook/config/hypr_shim.lua` + `hyprcfg.py`) | правка конфига меняет поведение |

Известное неустранимое различие: 60 Гц против 180 Гц (§9.1, §12).

### 5.2 Что работает (проверено вживую в прошлых сессиях)
- Центральный такт в WS: шаг ровно 16.67 мс без пропусков (замер 46/46, HANDOFF сессия 5); математика пружин и
  безье 1:1 с hyprutils (anim_feel §3–4, gap_review_2 п.5).
- Сдвиг-трансформ, альфа, серверная обрезка по видимой рамке (HANDOFF сессия 6).

- Configure через AX за 5–30 мс (порядок позиция→размер→позиция обязателен).
- Открытие с popin 86% + fadeIn; закрытие нашим M+Q с 92% + fadeOut; hide (fadeOut на месте).

### 5.3 Что точно НЕ работает (кратко; подробно — реестр §7)

нагрузка на главный поток WS опросом 60 Гц, наложения окон при быстром открытии.

## 9. Сводка по темам

### 9.1 Тайминг и 60 Гц
Источники: TM (главный), AF, WG §3, FP C2, GR2 п.5.

- **Кривые и параметры верны** (AF §0–4, GR2 п.5, TM §1): `spring_adv` = `advanceSpring` hyprutils во всех трёх
  режимах, финиш 0.001/0.001, безье 255 точек, `speed` у пружин игнорируется (как в Hyprland), retarget 1:1.
  Эталон Hyprland на видео ложится на теоретический drift с точностью ±0.03 (AF §2).
- **Часы движка устроены правильно** (TM §2.3, по бинарнику): точка сетки `te` = `nextWakeupTime` дисплея из CA;
  WS «защёлкивает» состояние окон через 0.5 мс после неё (`_CGXScheduleUpdateDisplay`); наш тик идёт в
  `te_prev + 0.1·T` с запасом ≈8 мс при опозданиях таймера до 7 мс → ошибка момента выборки 0, дрожи нет.
  Остаточный риск — опоздание тика на 13–15.5 мс (двойной шаг, потом ноль). Это закрывает опасение FP C2 /
  GR2 п.5 «фаза не измерена» — но **на экране это всё ещё не измерено**: нужны счётчики `te_skips`,
  `ticks_late`, `tick_us_max` и журнал траектории (TM §5 шаги 1–2).
- **Почему «резко» при верной кривой:** 60 Гц против 180 Гц. Пик шага drift на 60 Гц — 10% пути за кадр
  (147 px на половине экрана Air ≈ 1.9°), на 180 Гц у пользователя — 3.3% (≈0.86°). Наш скачок в 2.2 раза
  больше и держится в 3 раза дольше (TM §3.1, AF §0, WG §3.1).
- **TIME_SCALE** (`engine.py:20`, сейчас 1.2 на все кривые): форма сохраняется (k/s², d/s), пик 10.0 → 8.3%,
  95% хода 250 → 300 мс. Все три отчёта согласны, что это компромисс, не 1:1. Расхождение: TM — «оставить 1.2»,
  WG — «только геометрия, по умолчанию 1.0, A/B». **Решение пользователя/координатора: только геометрия**
  (Q4); финальное s выбирать A/B 1.0/1.2/1.35 после того, как уберём волны и задержки (TM §5 шаг 8).
- **Что реально даёт лёгкость на 60 Гц** (WG §3.3, TM §3.3, по убыванию): ноль задержки старта и одна волна
  (P10, P11); ни одного пропущенного кадра (P12, P13); округление к пикселю в хвосте (P22, Q5); правильная
  фаза (есть); motion blur — только путём композита и с потерей резкости текста (последний приоритет);
  **честные 180 Гц — подключить его монитор к Air по USB-C→DP** (тогда брать период дисплея окна, а не
  `display=1`, TM §2.3, WG §3.3 п.6).
- **Экзотика** (EX §1.4, [гипотеза]): отдать анимацию самому CoreAnimation (аддитивная `CASpringAnimation` на
  слое Server root окна) — шаг по развёртке на любой частоте, главный поток WS свободен. Один опыт (EX Ш3)
  решает, работает ли. Системный `PKGAnimation` — тупик (только 6 безье, без пружин, тот же таймер, EX §1.1).
- Безье в целых мс даёт ±4% неровности на 60 Гц (P25) → считать в double.
- Ретаргет Vector2D рвёт физическую скорость (свойство Hyprland) — решение пользователя (P24).

### 9.2 Управление окнами: configure/ack, ввод, hit-test
Источники: WC (главный), FP §2.2, WG §1.1–1.2, SK S3–S5, `notes/resize_re.md`.

**Размер приложению (configure).**
- Сервер не может сам поменять размер чужого буфера. Каналы «configure»: AX (сейчас, 5–30 мс, синхронный) и
  `_WMClientResizeWindowRequest` по BSService из WindowManager.app (resize_re.md §★★★; через lldb-мост 250 мс —
  снят). WM.app сам геометрию серверу задаёт только транзакциями `SLSTransaction*` (locked bounds, трансформ,
  клип, сдвиг с группой), размер — только запросом приложению (WC п.1).
- **Решение пользователя по каналу configure:**
  1. **Исследовать WindowManager.app** по трём критериям: (а) может ли он поменять размер нескольким окнам
     **одной атомарной транзакцией** (идеально под «одну волну на событие»); (б) идёт ли его команда через
     WindowServer **без синхронного ожидания ответа приложения**; (в) берёт ли он окна, которые **не
     управляются через Accessibility** или «упрямятся». Если хоть одно «да» — использовать WindowManager для
     этих случаев, AX оставить запасным; если все «нет» — остаёмся на AX и фиксируем вывод. Зацепки по строкам
     WM.app (WC п.1): `ApplicationClientResizeWindowRequestRegistry`, `awaitResponseForResizeRequest`,
     `ClientFenceGroup`, `LayoutDeferredFenceTracker`, `_lockedBounds` — похоже на пакетный запрос с fence
     [гипотеза].
  2. **Постоянное размещение нашего кода внутри WindowManager.app** (анонимная память) — в **конец очереди**:
     движение стартует с последнего показанного кадра, не дожидаясь приложения, поэтому выигрыш в миллисекундах
     не виден, а цена — ещё одна хрупкая точка при обновлениях.
  3. **`window_list_set_locked_bounds`** (186e50174) — кандидат для пустой полосы при росте окна у медленных
     приложений: сервер сам растягивает старый буфер на рамку L и атомарно переключает масштаб в момент
     коммита нового кадра (как niri). Оговорка: пользователь ранее резко не принимал видимое растяжение
     («как фотка») — внедрять только как вариант с **A/B-сравнением на видео** против «обрезка 1:1 + цвет края /
     клон старого содержимого», решать по виду.
- **Родной ack** (WC п.2): приложение коммитит новый размер транзакцией `SetWindowShape` (часто внутри своего
  CA-коммита, method 3) → сервер применяет форму и контент **атомарно** в `shape_window` и шлёт **807
  kCGSWindowDidResize** подписчикам (`SLSRequestNotificationsForWindows` + `SLSRegisterConnectionNotifyProc`).
  Изнутри WS то же видно как смена `bbox(win+0x170)` (движок уже читает) и `win+0xc4`. «Буфер нового размера
  пришёл» точнее — `GetLastChangeDataForContext` контекста приложения (CO §4).
- **Протокол одного события** (FP §2.2, WG §1.2, частично сделан в последней сессии): одна пачка → ждать
  `cmd_tail` → configure конечного размера сразу по обеим осям → немедленная проверка ответа → при отказе
  (минимум) ретаргет в следующем тике с сохранением скорости. Без таймеров `verify`/`realign`.
- **Гонки** (SK S3–S5): см. P6. Одна очередь configure на окно с «серийным номером» цели; один поток на
  приложение (AX-сообщения всё равно сериализуются его главным потоком).
- **Минимумы до раскладки:** `_SLSPackagesGetWindowConstraints` [гипотеза — заполняет ли AppKit для обычных
  окон; проверить одним вызовом на Finder]; иначе учить по ответу AX сразу (исправленное условие P2).

**Ввод и hit-test** (WC, всё [V] по листингу):

### 9.3 Композит: CA-дерево окна, буферы, скругления, снимки
Источники: CO (главный), EX §3, WG §1.4/§1.7, FP §2.3, SP §7.10.

- **Ключевая находка (CO §1б, EX §3.1, подтверждено листингом):** на macOS 26 у каждого окна внутри WS есть
  собственное дерево CoreAnimation в локальном CA-контексте WS:
  `Server root (cwc+0x80) → Shadow (+0x88) → Hosting (+0x98) → Window (+0x90) → Client Content Host (+0x60)`,
  `cwc = *(CGXWindow+0x18)`, CAContext `cwc+0x38`. Родное скругление = `Hosting.masksToBounds + cornerRadius +
  continuous`; родная тень = `Shadow.shadow*`; трансформ окна = `Server root.transform`; альфа = `opacity`.
  Рисует это QuartzCore прямо в кадр WS в правильной глубине (`___MetalCompositeLayer_block_invoke`).
- Наш клип `set_window_list_global_clip_shape` работает уровнем **выше** (экранная форма) и режет и CA-скругление,
  и CA-тень → P3.
- **Решение (CO §3, EX §3.3):** видимая рамка B = **маска на слое Hosting** (CAShapeLayer с суперэллипсом r=18,
  p=2.6, или CALayer cornerRadius 18 continuous), рамка-градиент/glow — свои слои над Shadow, тень — свой слой
  под Shadow (9-slice по формуле Hyprland), блюр — backdrop. WS не трогает маску Hosting и чужие подслои Server
  root (setMask только на root по биту 8, setSublayers — только у Drag Fade; маску на Server root ставить
  нельзя — WS её сбрасывает). Наши слои надо переустанавливать при пересоздании контента окна
  (`initialize_ca_content_for_context`). Писать — на главном потоке WS в `WSCAContextScopeTransaction`.
  [гипотеза: ось Y слоёв и частота перезаписи bounds — тест CO шаг 2.]
- **Отвергнутые варианты:** R-shape через `shape_window` (FP §2.3, WG §1.4) — делает `CGXBackingStoreResize` и
  шлёт уведомление приложению (WC п.2) → риск перерисовок; ступенчатый CGRegion — без сглаживания; `set_corner_radius(18)`
  сам по себе (EX Ш1) не спасает углы на обрезанной стороне, пока стоит глобальный клип (полезен как
  базовая форма углов в покое).
- **Содержимое при resize** (P4, P5): пока буфер меньше B — дотяжка края (второй `CALayerHost` того же
  контекста, обрезанный до крайнего столбца и растянутый, или `Hosting.backgroundColor` = цвет края); пока
  приложение не прислало кадр нового размера — **клон старого содержимого** (`CreateCloneOfWindow`) по
  `GetLastChangeDataForContext` (CO §4). Альтернатива — locked bounds (растяжение, только A/B, §9.2).
- **Снимок закрытия** (P16): `CreateCloneOfWindow(win, A, display, server_owned=true)` (18709e984) — готовый
  клон-окно; момент — колбэк `WSAddNotificationCallback` на **0x3e9** (синхронно в `release_window`, до order-out
  и `~CGXWindow`, окно и контент ещё живы; перепроверено) или **0x538** (finish order, op=out). Это поправка к
  WG §1.7 «EV_GONE — поздно, держать тёплый снимок»: тёплый снимок — только запасной путь.
- **Свой Metal-шейдер в глубине окна** (точный dual-kawase, clamp-to-edge, суперэллипс с АА) — только вставкой
  своего `WSCompositeSourceLayer` с backing, у которого vtable+0x20 = наш `RenderToDestination`, в момент сборки
  (`Compositor::prepare_layers`) — требует перехвата кода [гипотеза: патч __TEXT через `mach_vm_protect
  (VM_PROT_COPY)` при `amfi_get_out_of_my_way=1` — не проверено]. Это «путь Б».
- `metalCallbacks` рисует после всех слоёв — поверх всего (z-проблема подтверждена, CO §1). Для оформления не
  годится.

### 9.4 Фокус и «серые неактивные окна»
Источники: WG §2 (главный), EX §5.2, сообщения координатора.

- **Механизм** [V]: AppKit рисует активный вид по `hasKeyAppearance || hasMainAppearance`
  (`_hasActiveAppearance` 184a1392c), `isActive` там не проверяется. Биты ставятся в `becomeKeyWindow` →
  `acquireKeyAppearance` только у активного приложения. Деактивация — серверный `kCGSEventSuspend` 0x14 из
  `SetFrontProcessInternal` (перепроверено: `mov w1,#0x14` @186d51bf8). Серверного флага «всегда активный вид»
  нет (WG, EX — согласны); `WSSetWindowHasActiveAppearance` меняет только серверную тень.
- **Вариант A** (досылка Resume 0x13 через `SLPSPostEventRecordTo`) — **❌ проверено вживую, не работает**
  (§5.1).
- **Основной путь (согласие пользователя получено):** код в процессах приложений. Рычаг AppKit [V]:
  `-[NSWindow _setForceMainAppearance:YES]` (185748380) + `-[NSWindow _setForceActiveControls:YES]` (184bae330)
  на всех окнах приложения; для новых окон — по `NSWindowDidBecomeVisible`/`NSWindowDidUpdate`/`DidBecomeKey`/
  `DidResignKey`. После этого `_hasActiveAppearance`/`_hasActiveControls` = YES без key-окна.
  **Целевое поведение:** каждое тайловое окно всегда выглядит активным (цветные светофоры, активный фон и
  вибранс), как в Hyprland; клавиатурный фокус по-прежнему следует за курсором (окно под курсором получает
  ввод); системный тулбар/меню-бар не трогаем. Побочки: курсоры ввода — по-прежнему только у key-окна (это
  правильно).
- **Запасной путь:** перехват Suspend 0x14 внутри WS (WG §2.3 B/C): `PostCGSEventToProcess` статическая; вход —
  `__XSetFrontProcess`/`SetFrontProcessInternal`; демон инициирует почти все смены фокуса сам, остальное ловить
  `foregroundSwitchNotifyProc`. Требует патча пути/перехвата — дальше и рискованнее.
- **Фокус как в Hyprland:** follow_mouse без подъёма (P15/Q3); фокус окна внутри приложения — двумя event
  record (работает, как yabai); серверные понятия key-фокуса: `_SLPSStealKeyFocus`, `managed_space_set_key_window`.
  Единственный честный индикатор фокуса — рамка-градиент (§9.6).

### 9.5 Рабочие столы
Источники: AC §3.6, WG §1.9, FP §2.5, EX §2/§4, AF §2 (L7), SP §4, DR п.2/п.13.

- Эталон: slidefade 12% ширины + альфа, оба стола по drift, один t0, обои/меню стоят (AF L7 — измерено 307 px =
  12% на 2560; **video_audit ошибочно описал это как кроссфейд без сдвига**, см. §10 К2).
- Все согласны: **виртуальные столы внутри одного системного Space** (как AeroSpace); бинды M+1..0,

- Как анимировать — три варианта:
  1. смещение/альфа **стола** как отдельная переменная движка, прибавляемая к B всех его окон (AC §4.2) —
     рекомендовано (правильно сочетается с уже едущими окнами);
  2. `geom` каждому окну со сдвигом той же кривой (проще, но ломается при ретаргете);
  3. свой неуправляемый Space в WS и `PKGSpaceSetTransformWithConnection`/`PKGSpaceSetAlphaWithConnection`

     [гипотеза; прототип EX Ш5].
- Прятать окна неактивного стола: после ухода — server order-out (EX §4), при самопроизвольном появлении — снова
  order-out; запасной — увод за экран (сейчас так прячется hide).
- Пока системные Spaces остаются: на время системного перехода движок снимает свои трансформы (P30).

### 9.6 Оформление (рамка, тень, glow, блюр)
Источники: SP §5 (формулы), CO §3, EX §3, AC §3.3, FP §2.4, DR п.12.

- **Рамка** 2 px снаружи контента, градиент primary→tertiary по формуле `progress = 0.707·y + 0.293·x` в OkLab,
  α 0.933; неактивная outline_variant α 0.333; кроссфейд border 600 мс smooth; внешний радиус 20 (SP §5.1).
  Реализация: `CAGradientLayer` + маска-кольцо `CAShapeLayer` в Server root над Shadow (CO §3 п.3). Градиент CA
  линейный по точкам — формулу Hyprland «не поворот, а аппроксимация» повторить подбором start/endPoint или
  своей картинкой (OkLab-интерполяцию — запечь). Нативный `Shadow.borderColor/Width` (EX §3.2) — одноцветный,
  градиента нет — не 1:1.
- **Тень**: профиль `(1−e/34)^3` от бокса с рамкой, offset (0,10), активная 0.467 / неактивная 0.267, кроссфейд
  800 мс; рисуется под окном, внутри контента вырезана. Варианты: серверная тень (`SLSSetWindowShadowParameters`
  σ≈11, density ≈0.91) — близко; свой слой под Shadow с 9-slice картинкой по формуле — 1:1 по профилю.
- **Glow**: внутрь, range 18, primary α 0.2 только у активного, кроссфейд 800 мс (SP §5.4) — свой слой над Window.
- **Скругление**: суперэллипс p=2.6, r=18 (поверхность 17). CA `continuous` близко, но не 1:1; точный —
  CAShapeLayer-маска с путём суперэллипса (АА CA) — практически 1:1.
- **Блюр**: только под прозрачными окнами; тайловые — блюр **обоев** (кэш). Ближайшее без Metal — backdrop-слой
  WS (`SLSSetWindowBackgroundBlurRadius`/внутренний путь, гаусс) + свои `colorSaturate`/`colorBrightness`
  [гипотеза: WS перезапишет filters при смене радиуса]. dual-kawase 1:1 — только путь Б.
- В раскладке вычитать `border_size=2` с каждой стороны (P19).
- Палитра — скопировать `colors.lua` (P39).

Правила для каждого шага: к живому WS лезет только основной агент, один за раз; движок — только через перезапуск

## 12. Что физически нельзя 1:1 и как максимально приблизиться

| Предел | Почему | Как приблизиться | Источник |
|---|---|---|---|
| 60 Гц вместо 180 Гц | панель Air; смаз sample-and-hold в 2.2 раза больше | ноль задержки, одна волна, 0 пропусков, квантование хвоста, TIME_SCALE геометрии по A/B; motion blur (путь Б, мылит текст); **внешний 180-Гц монитор** | TM §3, WG §3, AF §0 |
| Скорость перерисовки приложения (Telegram, Electron, Finder 100–300 мс) | приложение владеет своим буфером | старый буфер (клон) обрезан/дотянут в правильной рамке, никакого серого; configure в первом кадре события | WG §1.5, CO §4, FP §2.6 |
| Configure до первого кадра нового окна | у Hyprland `predictSizeForNewTiledTarget` в xdg-configure; у macOS приложение создаёт окно своего размера | прятать по 0x3e8/EV_NEW, configure сразу, popin когда буфер готов | WG §1.8, SP §3.1 |
| Суперэллипс p=2.6 с АА и dual-kawase с vibrancy/brightness/noise | нет своего шейдера в глубине окна без перехвата кода | CAShapeLayer-маска суперэллипса (практически 1:1); гаусс-backdrop + фильтры; полный 1:1 — путь Б | CO §1в/§3, SP §5 |
| Хит-тест во время анимации | клик по трансформу видит кадр `te`, экран — прошлый; Catalyst игнорирует чистый сдвиг | ≤1 кадра — незаметно; ε-масштаб для Catalyst | WC |
| Системные анимации (Mission Control, нативный fullscreen-Space, Dock, Stage Manager, системный тайлинг macOS 26) | живут мимо нас | виртуальные столы, свой fullscreen, отключить в настройках | FP §4, DR п.10 |
| Пиксель ≠ pt | числа конфига в px Linux (109 ppi), на Air pt ≈128/дюйм | оставить числа в pt (на ~15% мельче) или ×1.17 — решение пользователя | FP §4 п.6, SP §7.9 |
| Вкладки = отдельные окна (Ghostty/Finder) | так устроен macOS | переименование листа + α=1 (P1) | SK S1 |
| Активный вид неактивных окон без кода в приложении | серверного флага нет | код в процессе (П3, согласие есть) | WG §2, EX §5.2 |
| Ретаргет Vector2D со скачком скорости | так в самом Hyprland | 1:1 или «лучше» по выбору пользователя | TM §1.1 |
| Меню-бар, системные меню, уведомления, OSD | системный UI | не трогаем (пользователь так решил для меню-бара) | AC #20–23 |
